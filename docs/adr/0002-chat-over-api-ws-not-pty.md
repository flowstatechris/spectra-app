# Chat runs over /api/ws JSON-RPC, not the /api/pty byte stream

Spec v2 §2.3 modeled chat as raw UTF-8 text over `/api/pty` with three sockets per profile (PTY + events + RPC). Live-wire testing against the real server showed `/api/pty` emits raw Ink TUI ANSI (alt-screen redraws, box-drawing frames) — unrenderable as message bubbles without a terminal emulator — while `/api/ws` exposes the full structured chat surface the Electron desktop itself uses: `session.create`/`prompt.submit`/`session.history` RPCs, `message.start`/`message.delta`/`message.complete` + `status.update` + approval/clarify events, and `profiles.list` with the rich per-profile metadata §2.2 believed was CLI-only. Events arrive on the RPC socket directly, so the `/api/events` pairing requirement disappears too.

Decided: Spectra connects **one `/api/ws` socket per backend** and scopes chat per session via `session_id`; `/api/pty` and `/api/events` are not used. This also sidesteps the server's 16-session PTY cap entirely (it is `PtySessionRegistry`-specific) and replaces the two-step `/image` slash-command upload with the `image.attach` RPC. If a terminal-rendering feature is ever wanted, the PTY transport can be added back for that screen alone.
